# Memento Constitution

## Core Principles

### I. Single Event, Single Host
Memento serves exactly one real event (a wedding) for its entire lifetime. There is no
multi-tenancy and no concept of supporting multiple events, organizations, or accounts.
Authentication is a single PIN-based host session — there is no user registration, no
per-guest accounts, and no roles beyond "host" and "guest with the link". Any design that
introduces tenant IDs, org scoping, or a general-purpose accounts system MUST be rejected.

### II. YAGNI / Build for the Users We Have
Build only for the users and problems that exist right now — one host, the wedding guests
who have the event link, and the traffic of a single event. Do not add infrastructure,
abstractions, caching layers, or scale-handling for load, users, or features that are not
currently real. Speculative extensibility ("what if we need multi-event support later")
MUST NOT influence current implementation decisions.

### III. One Application, No Separate Services
Next.js is the entire application: it serves the frontend and handles all backend logic via
API routes and/or Server Actions. There is no standalone backend service, no separate API
server, and no microservices. All server-side logic lives inside the Next.js project.

### IV. Raw SQL, No ORM (NON-NEGOTIABLE)
All database access uses raw SQL via the `pg` library talking directly to Postgres. No ORM
(e.g., Prisma, Drizzle, TypeORM) may be introduced. This is intentional: the developer is
learning SQL and Postgres directly before adopting any abstraction layer. Query logic must
be explicit and reviewable as SQL, not generated by a query builder or ORM.

### V. Synchronous by Default
No queue, no background job processing, and no realtime subscriptions until a real, observed
need for them appears. All features are implemented as synchronous request/response flows
unless a concrete, measured problem (not a hypothetical one) justifies otherwise. Adding
async infrastructure preemptively is a constitution violation.

### VI. Open Access, No Gating
Everyone who has the event link sees everything. There are no payments, no subscription
tiers, and no content gated behind thresholds (upload counts, view counts, time windows,
etc.). Access control is binary: has the link (and PIN, for host actions) or does not.

### VII. Server-Only Data Access
Supabase's Data API is disabled. All database access happens server-side, exclusively from
Next.js API routes / Server Actions. The browser MUST NEVER talk to Postgres or Supabase
directly. Any client-side code that holds a database connection string or bypasses the
Next.js server layer is a violation.

## Deployment & Operations

Deployment is Vercel, connected to the GitHub `main` branch, with auto-deploy on every push
to `main`. There is no separate staging infrastructure, no manual deployment gate, and no
additional environments unless a real need is observed and documented as an amendment.

## Development Workflow

When a decision is not explicitly covered by this constitution, it MUST be flagged as an
open question (e.g., in the spec's `NEEDS CLARIFICATION` markers or plan's Complexity
Tracking section) rather than resolved by assumption. Implementers must not silently
introduce multi-tenancy, ORMs, queues, realtime features, payments, or additional services
to "future-proof" the app — any such need must be raised explicitly and, if approved,
folded back into this document via an amendment.

## Governance

This constitution supersedes all other practices, templates, and prior conventions for the
Memento project. Amendments require: (1) a documented rationale referencing the specific
observed need (not a hypothetical), (2) an update to this file with a version bump per the
semantic versioning policy below, and (3) a check of dependent templates
(`plan-template.md`, `spec-template.md`, `tasks-template.md`, `checklist-template.md`) for
consistency.

Versioning policy: MAJOR for backward-incompatible governance changes or removal/redefinition
of a principle (e.g., dropping the single-event constraint); MINOR for adding a new principle
or materially expanding guidance; PATCH for clarifications and wording fixes.

All plans and reviews MUST verify compliance with these principles, in particular Principles
III, IV, V, VI, and VII, which directly constrain architecture choices. Any complexity or
deviation must be justified in the plan's Complexity Tracking section or rejected in favor of
a simpler approach.
